给博客做网页管理端的时候，第一个架构决定就把自己问住了：文章和站点数据存哪？直觉答案是"当然上个数据库"——轻量点的话 SQLite 一个文件就搞定。最后我没这么做：**管理端的每一次保存，落下来的都是仓库里的文件**。文章是 `src/content/posts/` 下的 Markdown，站点数据是 `src/data/` 下的 JSON。

这不是懒，是想明白之后的选择。

## 静态站的事实源必须是文件

这个站是 Astro 静态构建的：构建器读 Markdown，产出纯 HTML。如果内容住在数据库里，只有两条路——

- 构建时先连库把内容导出成文件再构建：数据库成了"最终还是要变回文件"的中间层，还多一个构建依赖，库不在线就构建不了；
- 放弃静态构建，改成请求时现查现渲染：部署形态、性能、成本整个变掉，为一个管理端把架构推倒，本末倒置。

既然终点一定是文件，那就让文件直接当事实源，数据库这一层根本不必存在。

## Git 白送的三样东西

内容落成文件之后，版本管理是**免费**的：

1. **历史与回滚**——每篇文章每次改动都有 diff，写崩了 `git checkout` 就回来，误删有 `git log` 兜底。用数据库的话，这套能力要自己设计备份和审计表。
2. **可迁移**——内容就是一目录 Markdown，哪天换框架、换平台，文件拎着就走。没有"从数据库导出"这个步骤，也就没有导出格式的锁定。
3. **不锁死编辑方式**——管理端能改，VS Code 也能改，手机上用 Git 客户端也能改。数据库里的内容只有管理端一个入口，入口挂了内容就成了黑箱。

这套思路不是我发明的，Decap、Sveltia、TinaCMS 这批 git-based CMS 就是同一个架构，我只是做了个自托管的迷你版。

## 数据库并没有缺席，它在管它该管的

站上真正动态的东西——点赞、阅读计数——在 Go 服务的 SQLite 里。这个分工值得说清楚：

| | 创作内容 | 访客数据 |
|---|---|---|
| 谁产生 | 我 | 访客 |
| 变化频率 | 一天几次 | 一天几百次 |
| 需要历史吗 | 需要（git） | 不需要 |
| 归宿 | 仓库文件 | SQLite |

写入频率高、单条价值低、不需要版本历史——这是数据库的主场。反过来，文章一天改不了几次，却极需要历史和 diff——这是 Git 的主场。**"要不要数据库"是个伪问题，真问题是哪类数据归谁管。**

## 实现里两个值得记的细节

**front-matter 要能往返**。管理端 GET 一篇文章、原样 PUT 回去，文件必须逐字节不变，否则每保存一次就多一层空行、diff 全是噪音。解析时剥掉正文首尾换行，序列化时写死一种规范格式，才能做到往返相等。

**JSON 落盘要保键序**。Go 的 `map` 反序列化再序列化会把键排成字典序，站点数据文件每存一次键就全洗一遍，git diff 没法看。改用 `json.Indent` 直接格式化原始字节，键序跟着客户端走，diff 里只出现真正改过的行。

## 图片也进仓库，但有代价

没有对象存储的话，图片跟着内容进仓库是最省事的：封面、插图、头像各有各的目录，上传接口负责放对位置。唯一要清醒的是 **git 仓库体积只增不减**——删掉的图在历史里永远占着地方。所以大图先压成 webp 再传，视频这种量级的东西永远别往仓库塞。
