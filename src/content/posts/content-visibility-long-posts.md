给博客做性能优化时列过一条"文章加虚拟滚动"。研究了一圈，结论是：**对静态长文，真·虚拟滚动是反模式；它想要的东西，CSS 原生就有**。

## 虚拟滚动在解决什么

虚拟滚动（windowing）的思路是只把视口附近的条目放进 DOM，滚出去的移除。它诞生于"上万行的动态列表"场景——聊天记录、无限流、大表格。代价也很明确：

- 移除的内容**不在 DOM 里**，`Ctrl+F` 页内搜索找不到；
- 锚点跳转（目录点标题）要自己实现"先滚到虚拟位置再渲染"；
- 高度必须可预估，图文混排的文章段落恰恰高度不齐；
- 需要 JavaScript 运行时——静态博客好不容易做到零 JS 阅读，为这个再背回来不值。

一篇几千字的文章撑死几百个 DOM 节点，根本没到需要 windowing 的量级。慢的不是节点数，是**首次渲染时给所有段落做布局和绘制**。

## content-visibility: auto 正中要害

```css
.article-body > * {
  content-visibility: auto;
  contain-intrinsic-size: auto 96px;
}
```

第一行告诉浏览器：这个元素不在视口附近时，**跳过它的布局和绘制**，滚近了再算。跳过的部分依然在 DOM 里——页内搜索照常命中（浏览器会自动把它渲染出来再滚过去），锚点、选中复制、SEO 全部无损。这正是虚拟滚动想要的性能收益，去掉了它所有的副作用。

第二行是配套的占位尺寸：没渲染的元素高度未知，不给个估值滚动条会随着滚动不断跳。`auto 96px` 的意思是"没算过就按 96px 占位，算过一次就记住真实值"——`auto` 关键字让回滚时用缓存尺寸，滚动条稳得很。

## 用在哪、别用在哪

这个站用在两处：文章正文的直接子元素（段落、代码块、列表各自独立跳过），和归档页的每一行文章条目。原则是**只给"视口外大概率存在"的内容**加：

- 长文正文、长列表 ✅
- 首屏内容 ❌——首屏本来就要立刻渲染，加了反而多一次判断
- 高度参与布局计算的元素（比如 `position: sticky` 的参照容器）要小心，占位估值不准会造成粘性判定抖动

## 效果怎么量

DevTools 的 Performance 面板录一次刷新：加之前，Layout 一口气算完整篇文章；加之后，首次布局只算视口内那几块，剩下的摊到滚动过程里，主线程的长任务直接矮下去一截。

> 浏览器早就内置了"按需渲染"，只是默认关着——因为只有作者才知道哪些内容可以晚点画。`content-visibility` 就是把这个开关交给你。

Chrome 85 起支持，Firefox 125 跟上，Safari 18 也有了。不支持的浏览器会当没看见这条属性——纯粹的渐进增强，没有任何回退成本。
